了解 Lore 在会话的每一步向 Agent 发送什么、Agent 怎样使用这些内容，以及 Lore 会记录什么。想弄清楚 Agent 为什么看到了某条记忆，或者哪些设置可以调整，就从这里开始。

## 会话开始

会话开始时，Lore 按以下顺序发送四项内容：

1. **全局使用规则。** 服务器管理的 Lore 使用说明，可以在设置中编辑。对应设置项为 `lifecycle.guidance.enabled`，默认开启。
2. **启动记忆（boot）块。** 下文说明的固定基线。
3. **启动召回。** 可选。根据工作目录和仓库名选出的候选记忆。
4. **技能列表**（仅 Loremem 云服务）。`<available_skills>` 列出 Agent 可以使用的技能。

### 启动节点

启动节点是固定的，因此每次会话都从同一份基线开始。

| 节点 | 内容 | 加载范围 |
| --- | --- | --- |
| `core://agent` | 所有 Agent 的工作流规则 | 所有运行时 |
| `core://soul` | 风格和人设 | 所有运行时 |
| `preferences://user` | 关于你的稳定上下文 | 所有运行时 |
| `core://agent/<client_type>` | 某个运行时专用的规则，例如 `core://agent/claudecode` | 仅当前运行时 |

### 技能（仅 Loremem 云服务）

Agent 能看到每个已启用技能的名称、描述和 `skill_id`。它会自行判断何时需要某个技能，并用 `lore_skill_get` 加载它。你也可以在提示词中输入 `$skill-name`，直接运行已启用的技能。

## 每条提示词：召回

每次提交提示词之前，Lore 会查找与之匹配的记忆，并加入一个 `<recall>` 块：

```text
<recall session_id="sess_8f3c" query_id="q_41" phase="prompt">
0.82 | project://checkout_api/webhooks | refund · idempotency key
0.71 | project://checkout_api/testing | flaky test · fake clock
0.64 | preferences://user | test first
</recall>
```

每一行依次是分数、URI 和命中的线索词。这一行只是线索，不是事实。依赖它之前，先打开这个节点。

Lore 默认采用以下展示规则：

| 规则 | 默认值 | 作用 |
| --- | --- | --- |
| 最低分数 | 0.60 | 低于该分数的候选不展示 |
| 最多行数 | 3 | 每个块最多 3 行 |
| 查询长度 | 200 个字符 | 查询内容截断为 200 个字符 |
| 超时 | 2000 ms | 召回太慢时直接跳过，提问照常进行（[详情](/documents/recall#展示规则)） |

设置项的键名列在[设置项参考](/documents/reference/settings)中。

召回会根据以下因素为候选打分：路径、术语和查询词的精确匹配；术语和记忆视图的语义相似度；全文匹配。此外还有少量加分：优先级、多个视图同时命中，以及近期更新。近期加分的半衰期为 180 天；优先级 0 和 1 的记忆不会衰减。

## 会话期间：读取

Agent 需要某条记忆时，用 `lore_get_node` 打开它。如果 URI 来自 `<recall>` 块，Agent 还要带上该标签中的 `session_id` 和 `query_id`：

```json
{
  "uri": "project://checkout_api/webhooks",
  "session_id": "sess_8f3c",
  "query_id": "q_41"
}
```

只有 Agent 带着这些 ID 打开记忆时，Lore 才会把这条召回记为“采用”，因此分析能显示 Agent 真正用到了哪些召回结果。想浏览而不是召回，Agent 可以调用 `lore_search`（查询内容为空或为 `*`，并指定 `domain`），也可以调用 `lore_list_domains`。

## 会话期间：写入

Agent 用 `lore_create_node`、`lore_update_node`、`lore_move_node` 和 `lore_delete_node` 保存长期有效的变更。默认会执行两项写入检查：

- **优先级容量**：限制优先级 0 的记忆最多 5 条，优先级 1 的记忆最多 15 条。创建和更新时都会检查。
- **触发条件检查**：触发条件缺失，或使用“A 或 B”这样的写法时给出提醒。

Lore 会把每次创建、更新、移动和删除都记录在节点历史中，并标明是哪个运行时做的修改。

## 维护

- **Dream** 默认每天 03:00 运行，需要配置 View LLM。它直接用记忆工具执行修改，并把每项改动标记出来等你审查；最近一次运行可以整体回滚。详见 [Dream](/documents/dream)。
- **备份** 默认每天 04:00 运行。自托管服务器保留最近 7 份本地备份。Loremem 云服务的 **设置** 中，备份标签页提供相同的设置。详见[备份与恢复](/documents/maintenance/backups)。

## 集成如何工作

每个 Agent 通过轻量插件或 MCP 服务器接入。插件本身不携带提示词。每个生命周期事件都走同样的流程：

1. 运行时到达一个生命周期节点，例如会话开始或提交提示词。
2. 插件把事件发送到 `POST /api/lifecycle/event`，附上会话 ID、提示词文本（如有）和 `client_type`。
3. 服务器返回可以直接注入的文本：使用规则、启动记忆块或召回块。
4. 插件把这段文本交给运行时。

这种设计带来三个特点：

- **规则文本保存在服务器上。** 在设置中修改一次，所有已接入的 Agent 会在下一次会话或提示词时使用新文本。
- **`client_type` 标识运行时。** Lore 用它加载对应的启动节点，并按运行时统计召回和使用情况。其他 MCP 客户端需要在端点 URL 中带上 `client_type=mcp`。
- **插件故障放行。** 如果 Lore 无法访问或响应缓慢，插件什么都不返回，Agent 在该步骤中不使用记忆继续工作。

| 运行时 | 接入方式 | 自动启动与召回 |
| --- | --- | --- |
| Claude Code、Codex、ZCode | 带会话和提示词 hook 的插件，并附带 MCP 工具 | 是 |
| DeepSeek Harness | 原生插件，带会话和逐提示词 hook，并附带 MCP 工具 | 是 |
| OpenCode | 原生插件，提供 `lore_*` 工具（不使用 MCP） | 是 |
| Pi、OpenClaw、Hermes | 扩展、插件或记忆提供方 | 是 |
| 其他 MCP 客户端 | Streamable HTTP MCP 端点 | 否，需要自己调用 `lore_boot` |

## Lore 能看到什么

Lore 能看到以下内容：

- **提示词文本**，用来为这条提示词查找召回候选。
- **会话 ID**，把召回和使用情况关联到具体会话。
- **会话开始时的工作目录名**，以及该目录是 Git 仓库且配置了远程地址时，从远程地址中取出的仓库名。这是尽力获取的信息。
- **Agent 写入的内容**，例如新建或更新的记忆节点。

Lore 从不读取你的源代码文件。插件只向 Git 询问第一个远程仓库的地址。

Lore 还会保存召回事件用于分析。除非开启“包含召回事件”，备份中默认不包含这些事件。

> [!TIP]
> Agent 写入的内容会被原样保存。请不要把密钥、令牌和一次性笔记写进记忆。
